# Внутренняя архитектурная карта MVP

> Служебный файл наставника. Код создаёт Владислав; перед изменениями сверять с `TZ.md`, `ROADMAP.md` и этой картой.

## 1. Границы системы

```text
Browser
  ├─ Next.js frontend (порт 3000)
  │    └─ UI, маршруты, формы, HTTP-запросы
  │
  └─ Express backend (порт 4000)
       ├─ validation
       ├─ auth middleware
       ├─ route handlers
       └─ PostgreSQL (порт 5432)
```

Frontend не знает парольных хешей, токенов сессий и не обращается к PostgreSQL. Backend не рендерит страницы Next.js.

## 2. Репозиторий

```text
/
├─ frontend/                 # Next.js + TypeScript + shadcn/ui
│  └─ src/
│     ├─ app/                # страницы и layout
│     ├─ components/         # компоненты интерфейса приложения
│     ├─ components/ui/      # исходники shadcn/ui
│     └─ lib/                # маленькие общие утилиты
├─ backend/                  # появится на этапе Express
│  └─ src/
│     ├─ routes/
│     ├─ middleware/
│     ├─ services/
│     └─ db/
├─ TZ.md
├─ ROADMAP.md
├─ DESIGN.md
└─ LEARNING.md
```

## 3. Frontend MVP

Маршруты:

```text
/                 лента
/login            вход
/register         регистрация
/[username]       публичный профиль
/profile/edit     редактирование собственного профиля
/sessions         активные сессии
/post/[id]        пост и комментарии
```

Пока backend не готов, эти страницы показывают фейковые данные. После готовности backend фейковые данные заменяются HTTP-запросами, а структура интерфейса сохраняется.

## 4. Backend MVP

Минимальные endpoint-группы:

```text
/health
/auth/register
/auth/login
/auth/logout
/me
/me/profile
/sessions
/users/:username
/posts
/posts/:id
/posts/:id/like
/posts/:id/comments
```

Порядок слоёв одного запроса:

```text
HTTP request → route → validation → auth middleware (если нужен)
→ handler/service → PostgreSQL → HTTP response
```

Не создавать «controller/service/repository» ради красивых названий. Новый слой добавляется, только когда текущий файл начинает реально смешивать разные обязанности.

## 5. Данные PostgreSQL

```text
User 1 ── N Session
User 1 ── N Post
User 1 ── N Comment
User 1 ── N Like
Post 1 ── N Comment
Post 1 ── N Like
```

Обязательные инварианты:

- `User.email` уникален.
- `User.username` уникален.
- `Like(userId, postId)` уникальна.
- Удаление Post каскадно удаляет его Like и Comment.
- Backend проверяет владельца до изменения/удаления Profile, Post и Comment.

## 6. Сессии

```text
login + password
  → проверить passwordHash через Argon2
  → crypto random raw token
  → Argon2 hash(raw token) в Session таблицу
  → raw token в HttpOnly cookie

следующий запрос
  → cookie → hash token → активная Session → User
```

- JWT не использовать.
- Каждая авторизация создаёт новую Session.
- Logout/отзыв меняет состояние сессии; старый токен перестаёт работать.
- Сессия хранит userId, token hash, createdAt, expiresAt, revokedAt, IP, user-agent, устройство/браузер.

## 7. Последовательность реализации

1. Статичный UI ленты и навигация.
2. Все статичные страницы из DESIGN.md.
3. Express + PostgreSQL + таблицы.
4. User → register → login → sessions → auth middleware.
5. Profile → edit profile → sessions UI.
6. Posts → feed → likes → comments.
7. Проверка прав и edge cases.

## 8. Стоп-лист до MVP

Не добавлять: Redis, поиск, друзей, личные сообщения, уведомления, закладки, подписки, изображения, вложения, ссылки, теги, realtime, JWT, OAuth.
